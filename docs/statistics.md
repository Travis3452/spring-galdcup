# 서비스 통계

ADMIN 계정 메뉴의 **서비스 통계** 또는 `/admin/statistics`에서 조회한다. 운영 모니터링과 서비스 통계 화면은 상단 메뉴로 이동한다.

## API

| 경로 | 권한 | 동작 |
| --- | --- | --- |
| `GET /api/admin/statistics?days=30` | ADMIN | 전체 건수, 현재 DAU·WAU·MAU, 신규 가입 추이 |
| `POST /api/activity` | 로그인한 회원 | 서버가 확인한 회원과 현재 한국 날짜로 활동 기록 |

조회 기간은 `1`, `7`, `30`, `90`일만 허용한다. 기간 선택은 가입 추이에 적용한다. 활성 회원은 조회 시점의 오늘·최근 7일·최근 30일 기준이다. 통계 응답은 `Cache-Control: no-store`이며 서버 내부 조회 결과는 기간별 최대 15초 캐시한다. 한국 날짜가 바뀌면 이전 날짜의 캐시는 사용하지 않는다.

전체 회원은 현재 `USERS` 건수, 게시판은 폐쇄 포함, 게시글은 DB에 남아 있는 건수, 댓글은 `DELETED_AT IS NULL`인 건수다. 회원 탈퇴 시 전체 회원 수가 줄어든다.

## 신규 가입

`User.createdAt`은 기존 `USERS.CREATED_AT`에 매핑한다. 회원 생성과 동일한 JPA 트랜잭션에서 `USER_SIGNUP_EVENTS` 한 행을 저장한다. 기존 계정 로그인·토큰 갱신은 이벤트를 추가하지 않는다. 이벤트 저장 실패 시 회원 생성도 롤백한다.

가입 이벤트에는 회원 ID나 개인정보가 없어 탈퇴 후에도 남는다. 기존 회원의 무작위 과거 가입일은 이벤트로 이관하지 않으므로 신규 가입 차트에 들어가지 않는다.

## 활성 회원

프론트엔드는 로그인 상태의 홈·게시판·내 정보 화면 이용 시 활동 API를 호출한다. 최초 라우팅이 완료된 뒤 시작하며, 관리자·인증 콜백·약관 화면은 제외한다. 보이는 탭에서 화면 이동·다시 방문·사용자 조작이 있을 때 확인한다. 토큰 갱신이나 자동 폴링만으로 활동을 추가하지 않는다. 익명 방문자 수는 집계하지 않는다.

브라우저 실행 중 같은 회원·한국 날짜의 요청은 성공 후 생략한다. 실패하면 30초 후의 다음 활동에서 재시도한다. 여러 탭·기기나 새로고침으로 요청이 겹쳐도 DB의 `(USER_ID, ACTIVITY_DATE)` 기본키가 중복 행을 막는다. 중복 키는 별도 쓰기 트랜잭션이 롤백된 뒤 정상 중복으로 처리하고, 다른 DB 장애는 503으로 응답한다. 수집 실패는 게시글 작성이나 화면 이동을 막지 않는다.

- DAU: 한국 시간 오늘 활동한 고유 회원
- WAU: 오늘과 이전 6일에 활동한 고유 회원
- MAU: 오늘과 이전 29일에 활동한 고유 회원

회원 ID와 날짜를 클라이언트에서 받지 않는다. 삭제되거나 존재하지 않는 회원은 기록하지 않는다. 탈퇴 시 외래키의 `ON DELETE CASCADE`로 활동이 삭제되어 과거 활성 회원 통계가 줄어들 수 있다.

## 수집 초기 표시

새 메타데이터 테이블이나 이관 표시 컬럼은 추가하지 않는다. 가입·활동 테이블의 최초 기록일을 관측 범위의 보수적인 기준으로 사용한다. 이는 실제 기능 배포 시각과 다를 수 있다.

가입 이벤트가 전혀 없으면 가입 수와 차트를 미수집으로 표시한다. 최초 가입 기록일 이전 날짜는 `null`, 이후 관측 기간에 가입이 없는 날짜는 `0`이다. 최초 기록일 자체는 하루 전체를 수집했는지 알 수 없어 부분 집계로 표시한다.

활동 기록이 전혀 없으면 DAU·WAU·MAU는 `null`이다. 기록이 생긴 뒤에는 저장된 고유 회원 수를 반환하며, 각 조회 구간의 시작일이 최초 기록일 이전이거나 같은 날이면 부분 집계임을 표시한다. 기록이 있는 이후의 0명과 수집 전 상태를 구분한다. 수집 장애 중 놓친 활동까지 복원하는 기능은 없다.

## 환경과 검증

Oracle에는 `db/oracle/statistics` 스크립트가 이미 적용됐다. 이번 기능은 추가 DDL 없이 사용한다. 조회 SQL은 Oracle 19c에서 실제 Repository·Service로 확인했으며, 한국 날짜 경계·중복 활동·고유 회원 집계를 시험한 데이터는 모두 롤백했다.

기존 MySQL 개발 프로필도 조회 분기를 제공한다. 다만 새 활동 테이블은 JDBC로 사용하므로 Hibernate가 자동 생성하지 않는다. MySQL을 사용할 때는 동등한 테이블·외래키·인덱스와 기존 회원의 가입일 보정이 별도로 필요하다. MySQL 실DB 검증은 수행하지 않았다. 기존 `application-dev.yml`의 사용자 설정은 변경하지 않는다.

```sh
# backend/galdcup
./gradlew --offline test bootJar

# frontend/galdcup
node --test tests/*.test.js
npm run build
```

실제 수집과 대시보드를 사용하려면 변경된 백엔드와 프론트엔드를 함께 배포한다. 운영 DB 마이그레이션 완료와 애플리케이션 배포는 별도다.
